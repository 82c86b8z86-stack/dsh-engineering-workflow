# 计划审批（Workflow Planning）

规格管「做什么」，计划管「怎么做」。本技能合并了计划撰写与计划执行两段：先写出执行者零上下文也能照做的计划，批准后按计划执行到底。

## 硬门禁

> 计划必须通过 `exit_plan_mode` 呈现并获批。用户的口头同意——包括对你所问问题的确认回答——不批准任何东西，也不结束 plan mode；把确认后的决定折进计划，通过 `exit_plan_mode` 提交。批准之前不得修改文件、不得建立 todo 实施清单。

## 撰写计划

开始时宣布：「I'm using the workflow-planning skill to create the implementation plan.」

**保存位置**：`docs/plans/YYYY-MM-DD-<feature-name>.md`

**假设执行者**：技术熟练但对本项目工具链与问题域几乎一无所知、且测试品味一般的工程师。文档写清每步改哪些文件、写什么代码、怎么测。

### 范围检查

规格覆盖多个独立子系统？应该在需求澄清阶段已拆成子项目规格；若没有，先建议拆分——每份计划单独产出可运行、可测试的软件。

### 文件结构先行

定义任务前先画出要新建/修改的文件与各自职责：单元边界清晰、接口明确、每个文件单一职责；一起变的文件放一起；按职责而非技术层拆分。

### 任务粒度（Bite-Sized）

任务 = 携带自己测试周期、值得独立审查的最小单元。脚手架/配置/文档折叠进需要它们的任务；拆分只发生在审查者「可以拒绝一个任务而批准其邻居」的地方。每步一个动作（2-5 分钟）：

```
- [ ] Step 1: 写失败测试（含实际测试代码）
- [ ] Step 2: 运行测试确认失败（给出命令与期望输出）
- [ ] Step 3: 写最小实现（含实际代码）
- [ ] Step 4: 运行测试确认通过
- [ ] Step 5: 提交（给出 git add/commit 命令）
```

### 计划文档头部

```markdown
# [Feature Name] Implementation Plan

> **For agentic workers:** 用 workflow-subagents（推荐）或本技能内联执行本计划。
> 步骤用 `- [ ]` 复选框跟踪。

**Goal:** [一句话说明构建目标]

**Architecture:** [2-3 句方案说明]

**Tech Stack:** [关键技术/库]

**Spec:** [本计划所实现的规格文档路径——计划从规格论证而来]

## Global Constraints

[规格中的项目级要求——版本下限、依赖上限、命名与文案规则、平台要求——每行一条，
数值原文照抄。每个任务隐含包含本节。]

---
```

### 任务结构

````markdown
### Task N: [组件名]

**Files:**
- Create: `exact/path/file.js`
- Modify: `exact/path/existing.js:123-145`
- Test: `test/exact/path.test.js`

**Interfaces:**
- Consumes: [用到的既有签名]
- Produces: [后续任务依赖的函数名、参数与返回类型——执行者只看得到自己的任务]

- [ ] **Step 1: 写失败测试**（代码块）
- [ ] **Step 2: 运行确认失败**（命令 + 期望：FAIL）
- [ ] **Step 3: 最小实现**（代码块）
- [ ] **Step 4: 运行确认通过**（命令 + 期望：PASS）
- [ ] **Step 5: 提交**
````

### 禁止占位符（计划失败项）

「TBD / TODO / 稍后补充」「加适当的错误处理」「为上述内容写测试」（没有真实测试代码）「与 Task N 类似」（要重复代码——执行者可能乱序读）「描述做什么却不展示怎么做」。每步必须包含执行者所需的实际内容。

### 自审

写完计划后换双眼睛自查（不派 subagent）：
1. **规格覆盖**：规格的每节/每条需求都能指到某个任务？列出缺口并补任务。
2. **占位符扫描**：按上表红线搜一遍，就地修。
3. **类型一致性**：后续任务用的签名/属性名与前面定义的一致（`clearLayers` vs `clearFullLayers` 就是 bug）。

## 提交审批

- 若在 plan mode 中：把完整计划 markdown 通过 `exit_plan_mode` 提交（该调用必须是那次响应的唯一且最后一个工具调用）。被驳回就吸收反馈重新提交；不可用则留在 plan mode 请用户手动切模式。
- 若不在 plan mode（用户关闭了 plan mode 或会话不在该模式）：用 `ask_user_question` 请求明确批准，等用户答复。
- 获批后：`todo_write` 为每个任务建一项（这跟踪的是批准后的实施，不属于 plan mode 的规划期）。

## 执行移交（计划获批后）

向用户给出两个选项：

1. **子 Agent 驱动（推荐）**——每任务派发一个全新后台 subagent，任务间审查，快速迭代 → 加载 `workflow-subagents`。
2. **内联执行**——本会话按任务顺序执行，批处理 + 检查点 → 继续用本技能的执行规则（见下）。

## 内联执行规则（选择选项 2 时）

1. 重读计划，批判性审查；有疑问先向用户提出，无问题才建 todo。
2. 每任务：标记 in_progress → 严格按步骤执行（每步验证照跑）→ 标记 completed。
3. 全部完成后转入 `workflow-verification` 收尾。
4. **何时停下求助**：遇到阻塞（缺依赖、测试失败、指令不清）、计划存在致命缺口、验证反复失败——停下问，不要猜。
5. 未经用户明确同意，不在 main/master 分支上开始实现。

## 红线

| 念头 | 事实 |
| --- | --- |
| 「计划我口头说一遍就行」 | 计划只经 `exit_plan_mode` 或明确批准生效；口头点头不构成批准。 |
| 「先干起来，边干边补计划」 | 未批准计划上的实现 = 无合同施工；退回去走门禁。 |
| 「这步验证差不多就行」 | 每步的验证命令照跑并读输出；跳过验证 = 跳过计划。 |
| 「阻塞了我猜一个方案继续」 | 阻塞时停下问，不要猜；猜错的代价是重做加信任损失。 |
