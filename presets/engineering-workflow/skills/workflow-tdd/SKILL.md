# TDD 实现（Workflow TDD）

先写测试。看着它失败。写最小代码让它通过。

**核心原则：没亲眼看过测试失败，就不知道它测的是不是对的东西。**

## 铁律

```
没有先失败的测试，就没有生产代码。
```

在测试之前写了代码？删掉，从头再来。没有例外：不留作「参考」、不在写测试时「改巴改巴再用」、看都不要看。删就是删。

## 何时使用

**总是**：新功能、缺陷修复、重构、行为变更。

**例外（须用户同意）**：一次性原型、生成的代码、纯配置文件。

「这次跳过 TDD」的念头 = 合理化。停。

## Red-Green-Refactor

```
RED    写失败测试
  ↓ 验证失败方式正确（失败于功能缺失，而非拼写/环境错误）
GREEN  写最小实现
  ↓ 验证通过，且其他测试仍绿、输出干净
REFACTOR  清理（去重、改名、提辅助），保持绿，不加行为
  ↓
下一个失败测试
```

### RED——写失败测试

- 一个测试只验证一个行为；名字说清行为（`rejects empty email`，不是 `test1`）。
- 测真实代码而非 mock（除非不可避免）。
- 写你希望的 API：先写断言，再想实现——测试难写 = 设计难用，听测试的话。

### 验证 RED——亲眼看它失败（必做，永不跳过）

用 `pwsh`（Windows）或 `bash` 运行，确认：
1. 测试**失败**（不是报错）——失败信息符合预期；
2. 失败原因 = 功能缺失（不是拼写错误、不是环境问题）。

测试直接通过 = 你在测既有行为，改测试。测试报错 = 修环境问题重跑，直到它以正确的方式失败。

### GREEN——最小实现

写恰好让测试通过的最少代码。不加功能、不改别的代码、不做「顺手改进」。

### 验证 GREEN——亲眼看它通过（必做）

运行测试，确认：通过；其他测试仍绿；输出无错误无警告。测试失败 = 改代码，不是改测试。

### REFACTOR——清理

绿了之后才能重构：去重、改名、提辅助函数。保持绿，不加行为。

## 好测试标准

| 质量 | 好 | 坏 |
| --- | --- | --- |
| 最小 | 只测一件事；名字里有「and」就拆 | `test('validates email and domain and whitespace')` |
| 清晰 | 名字描述行为 | `test('test1')` |
| 示意图景 | 展示期望的 API | 掩盖代码该有的样子 |
| 诚实 | 断言真实行为 | 断言 mock 行为 |

改任何测试时，自问：说出能让这个测试失败的生产代码改动是什么——答不上来就别写。

## 缺陷修复

发现 bug？先写复现它的失败测试，走 TDD 循环。测试既证明修复，也防回归。**没有测试不修 bug。**

## 常见合理化（全是错的）

| 借口 | 现实 |
| --- | --- |
| 「太简单不用测」 | 简单代码照样坏；测试只要 30 秒。 |
| 「先实现，测试后补」 | 事后测试直接通过 = 什么都证明不了；你没看过它失败，就没证明它能抓住 bug。 |
| 「手动测过了」 | 手动测试没有记录、不能重跑、压力下会漏；「当时能用」≠ 全面。 |
| 「删掉重写太浪费」 | 沉没成本谬误；真正浪费的是保留一份不信任的代码。 |
| 「留作参考，测试照写」 | 你会「参考」它 = 事后测试。删就是删。 |
| 「TDD 拖慢速度」 | TDD 才是务实路径：提交前抓 bug、防回归、敢重构。 |
| 「探索一下再写」 | 探索完扔掉，从 TDD 开始。 |
| 「现有代码没测试」 | 你正在改进它——为新改动补测试。 |

## 验证清单（宣称完成前）

- [ ] 每个新函数/方法都有测试
- [ ] 每个测试都亲眼看过它失败
- [ ] 失败原因正确（功能缺失，非拼写/环境）
- [ ] 写了最小实现
- [ ] 全部测试通过、输出干净
- [ ] 测试测真实代码（mock 仅限不可避免）
- [ ] 边界与错误路径已覆盖

勾不齐 = 你跳过了 TDD。从头再来。

## 卡住时

| 问题 | 解法 |
| --- | --- |
| 不知道怎么写测试 | 先写希望的 API、先写断言；还不行就问用户。 |
| 测试太复杂 | 设计太复杂，简化接口。 |
| 什么都要 mock | 代码耦合过重，用依赖注入。 |
| 测试脚手架巨大 | 提取辅助；仍然复杂 = 简化设计。 |

## 最终规则

```
生产代码 → 存在测试，且该测试先失败过
否则     → 不是 TDD
```

没有用户许可就没有例外。
